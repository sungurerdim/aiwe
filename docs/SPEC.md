## 1. Purpose, users, problems, value, metrics
### 1.1 Purpose
aiwe turns a goal item into verified, merged code, using the AI subscriptions and API keys you already have. It runs
on Windows, macOS and Linux with zero configuration, through each provider's own CLI or API, never through a proxy.
Its primary interface is an MCP server that the user's harness session starts. It is a public open-source product.

Pillars, in value order:
1. **Verified delivery**: small units; only the engine runs checks; an independent auditor judges the done criteria;
   only audited tips merge; every unit is measured (§1.5). This is the differentiator (§17).
2. **Work tracking**: one work-item standard (§8.4, O31); a goal splits into unit items in an unlimited tree with `blockedBy` dependencies;
   `aiwe item` and `aiwe report` work across the user's repositories (O8).
3. **Source organization**: subscriptions and API keys are sources; each run gets its model from measured data
   (§8.1, O9) with ordered fallback (O3); quota status is shown and never forecast (§7.6); spend comes from the ledger
   with an optional cap; at most one consumer subscription per provider (O7); aiwe holds no credential (DR-19).

**Users**: solo developers and small teams who run several projects with coding agents; they act only on product decisions.
### 1.3 Problems and how each is solved
| Id | Problem | Mechanism |
|---|---|---|
| S1 | Extra subscriptions and API keys are not usable in a standard way. | One global source registry (§8.1). |
| S2 | Cost, time, errors and waste are minimised by hand. | Model choice and routing (§8.1), measured capacity (DR-3), quota reaction (§7.6), metrics (§1.5). |
| S3 | No standard role or task template. | Role cards and the work-item standard ship with the engine (§8.4, §9). |
| S4 | The writer approves its own work, checks are skipped, scope is vague. | DR-5, DR-6, DR-7, DR-9. |
| S5 | Context bloat on long work causes wrong or missing work. | Small units (DR-7), a clean context per run, a per-request context ceiling (§7.4, §10.2), state only in the work store and ledger (DR-20). |
| S6 | Agents run broad checks outside their scope; a 5 s check becomes 5 min. | DR-8, §7.8. |
| S7 | Agents do not work the same way. | One prompt contract, card format and return format (§9). |
### 1.4 Value order
When goals conflict: **1 time** (the user gives a goal and sees a result) · **2 trust** (every merged change passed a
mechanical gate and an independent audit; the change fail rate within its target, M3) · **3 cost** (lowest measured quota, money, disk, CPU,
memory and network).
### 1.5 Success metrics
`aiwe metrics [--repo R] [--since D] [--by goal|model]` computes them from the ledger (§8.5) and the git history of
the working branch (L10). The DORA and Flow measures derived from the lifecycle events are in §8.5.

| Id | Metric | Target | Exact definition |
|---|---|---|---|
| M1 | First-try green rate | ≥ 70 % | `A / B`. B = units closed `completed` in the window. A = units in B whose first engineer run merged with `fixRounds = 0` and no second engineer run. |
| M2 | Interventions per unit | 0 | Ledger records with `kind = owner_action` per closed unit. The engine writes one when it stops for the owner, or when it sees a non-engine commit, label or state change on a claimed unit. |
| M3 | Change fail rate (DORA) | ≤ 2 % over the last 50 batches (default) | `A / B`. B = batches fast-forwarded to `main` in the window. A = batches in B that a later commit C on the working branch touches within W after the batch's merge: C is a `git revert` of a commit of the batch, or is typed `fix` and changes lines that `git blame C^` attributes to one. W = 30 days (default). A unit-level case is an **escaped defect**; the report lists them beside the rate. Over the target → `goal_paused` (§7.4) and an `owner-action` item. A window with a removed ledger rotation reads `unknown` (§8.5). |
| M4 | Cost per green unit | measured | Sum of `costUsd` over all runs of units merged in the window ÷ number of those units. One unknown cost → `unknown` plus the measured lower bound. |
| M5 | Unit lead time | measured | Median (p50, with p85 beside it) of `ciGreenAt` minus the `at` of the unit's first `taken` event (§8.5) over units merged in the window. |
| M6 | Mechanical ratio (R12) | falling trend | Per workflow step the share of `[M]` and `[J]` runs; `judgement` done entries open; auditor runs per unit; manual lead or owner actions per week (manual close, manual confirm, hand-written trailer, hand-edited record). A judgement entry or a manual action seen a third time gets a mechanism. |
| M7 | Tokens per green unit | measured | Σ(`tokensIn + tokensOut`) over the runs of units merged in the window ÷ number of those units, with fresh tokens (`tokensIn − tokensCachedIn`) printed beside it. One unknown token count → `unknown` plus the measured lower bound. Regression: median of the last 20 > 1.25 × median of the 20 before → red in the report and `aiwe metrics`, plus an `owner-action` item. |
### 1.6 Glossary
**Work item**: one JSON file of the work store (§8.4); its `id` never changes. **Goal**: an item that groups child items, its units. **Unit**: an item in the standard (§8.4) with a file set and a
verify; the item id names it and its **finding key** (the item's `key`) is the identity a unit upsert matches on (R4). **Run**: one role (§9.1) on one unit by one source (§8.1); id = ULID.
**Harness**: a CLI program that runs an agent; an **adapter** drives one harness or API wire format (§10.2).
**Check**: one mechanical command with a recorded result and a **cache key** (`gates.CheckKey`, §7.8), run only by the **check executor** (`aiwe check <kind>`, §7.8); a **gate** is an ordered list of checks; `aiwe unit check` checks a unit (§8.4). **Evidence**:
engine-recorded command, exit code, last lines and cache key; agent text is never evidence. **Unattended**: no human waits;
every gate still runs. **Bridge**: the out-of-repository stand-in `aiwe-wt/` that works units until aiwe self-hosts (DR-23). It is the only runner until the landing queue (§6.5), slots and the work loop (§7.11) land; it gets bug fixes only, then retires (#269, L29), and a bridge unit closes with its evidence file (§6.3). **Slot**: a persistent clone of the repository in which one run works (§6.5), and nothing else. **Ticket**: a lease on part of the check executor's pool, the CPU admission of a check or heavy command (§6.6). **Claim**: the ownership of a work item, a lease file in the state root (§6.6). **Scope lease**: the planned file paths and globs of an active item (§6.6). The four leases are the slot (a workspace clone), the ticket (CPU admission), the claim (work ownership) and the scope lease (planned files); `aiwe item take` takes a claim, a scope lease and a slot in one call (§6.6). **Verdict record**: one role's answer on one item (role, `GREEN` or `RED`, evidence, run id, session), an event of the ledger (§8.5); the item's `reviews` only shows it (§8.4, §9.3). **Gate point**: a moment at which checks run: commit, narrow test, CI, merge or release (§7.10). **Fast gate**: the commit point plus the recorded unit verifies, run by the landing queue on every audited tip (§7.10). **Project profile**: the flags of a managed project that no tool can derive, and its project stage (§11.1). **Delivery stage**: a goal item G1 to G7 (G7b included) that builds one part of this design (§13).
## 2. Scope and non-goals
In scope: onboarding a git repository without setup (DR-4); planning a goal into unit items (§7.2); the unit
lifecycle to the merge (§7.3); sources, model choice, routing and quota reaction; ledger and metrics; item tooling
and reports across repositories (O8); an MCP server as the primary interface, with the CLI from
the same registry, and self-update (O10).

**End of job** for a unit: its commit is on the working branch behind a green batch CI run, and
the item is `done` with one of the evidences §6.3 names (L7).

Non-goals (permanent): an interactive app or server (a web, desktop or mobile UI, a terminal session manager, a chat bridge; a report is one static file, §8.5); a proxy or gateway for
model traffic (DR-19); a learned router whose choice can change without a change in its inputs (O9); storing
credentials (DR-19); reading logs, sessions or bills of tools aiwe did not run (O6); holding or reading a deploy credential, and running a deploy outside the project's CI (§7.8);
general pull-request review; a network MCP transport; deleting a directory aiwe did not create (DR-11); rotating
consumer accounts of one provider (O7); a forecast of anything outside aiwe's control, such as quota, price or provider limits (K34); benchmark harnesses and agent evaluation sets (K34). Deferred with a trigger: §15.

### 3.2 Rule system
A rule is written once, in the registry (L27); everything else cites its id.
- **Layers**: the registry `docs/standards.md` holds each rule (DR-n, STD-n) and, in its enforcement cell, how it is enforced. A catalogue row (§11.2) adds the rule's meaning in this system, a violation example, its check and its brake, and cites the registry id. A mechanism (hook, lint, gate step, generated CI file) opens with `enforces: <rule id>`. A role card holds its difference only (§9.5). The project's `AGENTS.md` holds project facts only, never a copy of a rule. CI runs the full test, build and scans and repeats no local work except as §7.10 allows.
- **Kind**: a rule is mechanical (enforcement `check` or `test`), judgement (`judgement: <role>`) or planned; the kind is read from the enforcement cell.
- **Rule registry and two-way lint** (L27; planned: stage rule registry): the registry holds every rule once, and the two-way lint turns red a mechanical rule that no mechanism cites and a mechanism that cites no registry id. A hook with no rule gets a rule or is deleted. A **host-neutrality lint** is one more line of it: a harness-specific string (a hook event name, a harness directory, a harness setting) is allowed only in an adapter data row (DR-3, O13).
- **Doc-lint** (commit point, 5 s default budget): runs on the rule, card and `AGENTS.md` files of the project and on the cards aiwe ships. It finds a paragraph repeated in two files; a dead path or reference; a file over its word ceiling (a setting, STD-13: it starts at the size of the largest such file and drops each time a file is shortened below it); a rule or principle name with no registry row ("apply SOLID" without an id).
- **Model tier**: one rule set loads for every model. Correctness rests on the mechanism: a weaker model's error is caught at the gate.
- **Learning loop**: a retrospective produces only a mechanism or a correction of an existing registry row. One rule in, one rule out; the word ceiling enforces it. An error class seen a third time gets a check at the earliest gate point that would have caught it (DR-12, M6).
- **External-advice filter**: advice from outside passes three questions: does it solve a problem we measured; does it replace something or sit on top of it; is it text or a mechanism. The answer is one line in the item or decision that takes or rejects it.
## 4. Engineering principles
KISS, YAGNI, DRY and SSOT (DR-17, DR-22) · open/closed: a provider is one adapter file plus one line in
`adapters/all.go` · dependency inversion: engine code depends on ports, never on an adapter id (§5.1) · pure core
(§5.6) · append-only ledger (test `ledger/store_test.go`) · idempotency: a "run twice" test per command · accessible
output: status words, no colour, `--format json` (test `core/output_test.go`).

**Control, economy, mechanism** (K34, K35, K36): aiwe takes on only what it manages and can act on. What lies outside it, such as a provider's quota or limits, is shown as status when it is known; no forecast, model or workflow rests on it. Economy is a design approach: the fewest tokens, the highest quality, the fewest errors; a function whose benefit does not clearly exceed its token, run and maintenance cost is deleted, and every revision of this specification checks that. A function that can be mechanical is mechanical and depends on no one agent, harness, provider or lead session: the rule lives once in the core and is enforced at a harness-neutral point (the git hook, the landing queue, a CLI or MCP call); a harness hook is a thin adapter that warns early.
### 4.1 Necessity gate (DR-22)
Before anything is added (code, a file, a page, a setting, a layer, a gate, a test, a rule), five questions get an answer: Is the problem proved? Does deleting solve it? Does it exist already? What is the smallest change, in files and lines? What happens if it is not done? No proof, no addition. **Basis** (K39): an element stays only if it rests on a named standard (a registry row of §3.1, or an external standard it cites, such as WCAG 2.2, the DORA names, SI units or ISO 8601 for a report) or a named need (a measured problem, recorded as `need.problemEvidence`); an element with neither is removed, and every revision of this specification and every audit applies the test. For a risk that is only possible nothing is added: the item records the risk, its likelihood and the complexity its fix would add (`need.risksNotAdded`), and work goes on; the agent does not stop to ask. Input validation, authorization, secrets and payments are outside this rule and are always done.
- **Mechanical part**: the `need` record of §8.4. An item with an empty `need` cannot start (DoR); `alternatives` needs at least one entry, so no plan is written without a considered alternative. `estimate` (files, lines) is compared with the diff at the commit point: a diff over 2 × the estimate is refused until the estimate is changed with a reason or the item is split.
- **Independent check**: it runs when `estimate.files` is over 5, or the item adds a dependency, a page or a gate; below that, work starts unchecked. The checker is an auditor run separate from the author (DR-5), in the order delete, simplify, fix: the first question is whether it is needed, so a needless page gets one finding, not forty. A finding cites a registry id (`STD-7: scope.new holds a settings layer with no second use`).
- **Mechanisms**:

| Mechanism | Catches | Gate point |
|---|---|---|
| Diff budget, 2 × the estimate | work that grew past its estimate | commit |
| Dependency gate (D17) | a dependency with no reason, absent from the registry or too new | commit |
| Complexity (Q12, step `lint`) | a KISS violation | commit |
| Dead code (step `deadcode`) | unused code, speculative generality | CI |
| Duplicate detector (a profile cell; planned) | a DRY violation, at the third copy | CI |
| Two-point lint (§7.10) | one check at two gate points | gate lint |
| Mutation on selected modules (STD-20) | a test that catches no defect | CI, weekly |
## 5. Coding rules and patterns
Paths are under `internal/`.
### 5.1 Ports and adapters
Ports: provider (§10.2), tracker (§10.1), stack profile (§8.2), sandbox (§6.7); each port carries `ID() string` (`core.Identified`; the provider port declares it itself). The
engine holds `[]adapters.Provider`, never a vendor type; auth, quota detection, resume and streaming live in the
adapter. `adapters.All()` is the one list of compiled adapters (test `adapters/all_test.go`); `Available(ctx, all,
env)` filters it at run time. An API source needs no code: its row names the compiled adapter that speaks its API format. Stack profiles, capabilities,
outcomes, checks, quota classes and role fit are data tables: a new stack is a row.
### 5.3 Result and error model
```go
type Status string // "ok" | "error" | "usage" | "red" | "no_change" → exit 0 1 2 3 4
type Result[T any] struct { Status Status; Outcome Outcome; Data T; Detail string }
type Error struct { Outcome Outcome; Expected, Found, Next string; Err error } // Unwrap() returns Err
```
A red gate or `no_change` is a `Result`; an `error` means the command could not decide. Callers wrap with `%w` and
test with `errors.Is`/`errors.As`, never by text. `core/outcomes.go` maps outcomes to exit codes. `panic` only for
programmer errors, through `core/assert.go`; entry points recover once, write a crash record and exit 1. Errors render
as `<outcome>: expected <x>; found <y>; next: <one action>`. Logs are one JSON object per line on stderr through
`log/slog` (`{ts, level, runId?, unit?, event, detail}`), no colour. Dependencies are struct fields or parameters. No package-level mutable variable except sentinel errors, compiled
patterns and `var version string` in `cmd/aiwe/main.go`. The environment is read only in `core/env.go`.
### 5.6 Pure core, imperative shell
Decisions take and return data; process, git, HTTP and file IO live in `*_io.go` files or adapters. Only those,
`cmd/aiwe/main.go`, `internal/cmd/repocheck/main.go`, `repocheck/source_rules.go` and the `core` files that
`ioCoreFiles` in `repocheck/source_rules_layout.go` lists import `os`, `os/exec`, `io/ioutil`, `net` or `net/http`. A
file under a repository or state root is read through an `*os.Root`, because a path read follows a link out of the
root; only the files `rootReadFiles` lists read by path (rule `root_read`; `os.ReadDir` and nil-source parser reads are
not covered). The root refuses an absolute link target; it cannot see a hardlink.
### 5.7 One command registry
`core.Command{Module, Object, Verb, Params, Purpose, Run}`; commands read `<object> <verb>` (`aiwe unit check`), or one word for
a single action (`aiwe version`). `Terminal: true` (planned with the first terminal-only command, #56) marks `sources enable`, `artefact submit`,
`unit approve-breaking`, `update --major` and `resume`: never an MCP tool; confirmation from the terminal; no terminal → `not_a_terminal`.
### 5.12 Config precedence
flags > environment > settings files (`<state>/settings.json`, `<state>/settings.*.json`) > defaults. A settings file
is opened once without blocking and must be a regular file of at most 64 KiB, else `config_invalid`.
`aiwe config show` prints each value and its origin. Paths resolve against `--repo`; a relative path without it is
`usage`; only a relative `--repo` resolves against the working directory, once, at the CLI boundary.
### 5.13 Test structure
- `x.go` has its behaviour test in `x_test.go`, or the covering test names it. Tests are table-driven; each row names the failure it catches. Every check has a red case on a known-bad input.
- One contract suite per port, run against every implementation and fake (`providertest.Run`, `trackertest.Run`); the provider suite checks recorded harness flags, lean runs, no credential leaving env, DR-15, DR-19, quota classes (§7.6).
- Parsers of untrusted text (item file, intake, `gate.json`, sources, catalogue) have a `Fuzz` test. Fixtures use realistic values, `t.TempDir()` and `core.CreateOwned`. Live calls sit behind the build tag `smoke`.
- Source file ≤ 400 lines; test file ≤ 500; non-test function ≤ 60 lines (Q23) and cognitive complexity ≤ 12 (Q12); a root package holds its public surface only. Enforced: `repo/size`; `gocognit`.
- The test step's limit is at least 2 × the longest recorded package, never divided by workers; a package over half the limit turns the gate red. `-p` comes from DR-3.
### 5.14 Text and locale
`core.ReadText` accepts UTF-8 only (`invalid_utf8`); `core.PassText` sends long or non-ASCII text by stdin or a UTF-8
file. Case mapping only on ASCII markers; byte comparison and order; ISO numbers and dates; no console code page is
read or set; Windows argv lives only in `core/process_windows.go` (§17).
### 5.15 Owned removal
`core.Owner.CreateOwned(ctx, root, owner)` makes a directory and its `.owner` marker under `TempRoot` or `CacheRoot`, the only `OwnedRoot` values; only `CreateOwned` makes an `OwnedDir`. `RemoveOwned` refuses (`not_owned`) unless all hold (L6): the real path is under the temp or cache root; no link leaves that root; the marker is present; the walk never descends into a mount point. The state root and user directories stay outside (Q14). The cache root is `root_unsafe` when it is or contains the home, the state root, an onboarded local repository or a file-system root, is a link or junction, or is not owner-only, as is any root another user can read, write or owns. The temp root is the operating system's temp directory (§6.4); it is shared, so only the directory aiwe owns beneath it is tested for owner-only mode; a bare clone or a slot in the cache root is aiwe's own data, not protected. The fix never names a directory for delete. A state root is `root_unsafe` (L18) when it is a file-system root, is or contains the home or an onboarded local repository, or lies inside an onboarded local repository's work tree.
### 5.17 Static analysis
`go vet` alone caught none of five tested classes (§17). Gate step `lint` runs golangci-lint from `tools/go.mod` with
`exhaustive`, `errcheck`, `errorlint`, `contextcheck`, `containedctx`,
`noctx`, `bodyclose`, `forbidigo` (`os.RemoveAll`, `os.Getenv`, `panic`, `context.Background` outside their one file),
`gocognit` (`min-complexity: 12`; a whole `switch` adds 1, so tables stay cheap), `gosec`, `staticcheck`, `unused` and
`govet`. `nilaway` (a module plugin that may report false positives) is planned (#365); the custom binary is not built. Data races: CI step `race`. Blocked goroutines: `testing/synctest`. Index range: table tests, fuzz seeds.
### 5.18 Context and goroutines
Every function that blocks, does IO or starts a process takes `ctx` first; a time limit is a `context.WithTimeout`
where it is owned; `context.Background()` only in `cmd/aiwe` and tests; no struct stores a context. Goroutines run
under `errgroup.WithContext` with `SetLimit(core.Workers(jobs))`; the first error cancels the rest (§17). Every
goroutine has a waiting owner; only the sender closes a channel.
### 5.20 Subprocesses and process trees
`core.Start(ctx, ChildSpec{Argv, Dir, Env, Stdin})` starts a child in its own process group (Unix `Setpgid`) or Job
Object (Windows); `StopTree(grace)` asks, waits, then kills the tree. `Cmd.Cancel` = `StopTree` and `Cmd.WaitDelay` is
set, so held pipes cannot hang `Wait`. For `.cmd` and `.bat` launchers the code builds `SysProcAttr.CmdLine` and
refuses an argument it cannot quote, because `cmd.exe` does not follow `CommandLineToArgvW` (§17). Lookup follows
`exec.ErrDot`. Enforced: test `core/process_test.go` on three OS.
### 5.21 Git calls
Every git call of the engine and `repocheck` goes through `core.Git` (DR-10) with `-c core.fsmonitor=false
-c core.hooksPath=<empty owned dir> -c protocol.ext.allow=never -c submodule.recurse=false`, and `--no-ext-diff
--no-textconv` on `diff`, `log` and `show` (§17). The `file` protocol serves only the engine's own slots. A hook or
`diff.external` written into a slot's `.git/config` cannot make the engine run it (test `core/git_test.go`).
## 6. Architecture
### 6.1 Modules and packages
The table of packages, responsibilities and allowed imports is `core.Modules()` in `core/modules.go` (DR-17); `repo/boundaries` compares it with `go list -deps -json ./...`. Decisions kept here: private packages sit under `internal/<m>/internal/`; `internal/repocheck`, `internal/e2e` and `internal/cmd/repocheck` are never shipped; `cmd/aiwe` imports root packages only, except `repocheck`.
### 6.2 Runtime and distribution
Decision (owner, 2026-10-10): Go, one statically linked binary for windows, darwin and linux on amd64 and arm64.
Basis (§17): the Go binary is the smallest, answers MCP `initialize` fastest, idles with the least memory and
cross-compiles without an extra download. Rejected: Node single executable, Bun, a Node runtime through `npx` (breaks
DR-4). GoReleaser builds with `CGO_ENABLED=0` and `-trimpath`; the version comes from the tag only. No source file is
architecture-specific (`repo/source-rules`). Channels: GitHub Releases (six archives, `checksums.txt`, `checksums.txt.sig`,
one attestation; a browser or `curl` is enough); the MCP Registry as package type `mcpb` (§17); winget (§17); Scoop;
a Homebrew tap as a cask, since formulas are deprecated there (§17).

git is the only prerequisite. At start the binary runs `git --version`: missing → `git_missing`; older than the oldest
version that passes the git tests → `git_too_old`; both exit 1 with the next action. Reason: go-git has no rebase and
no patch apply (§17). The tracker needs no extra program: gh is optional (§10.1, L3). Harnesses are optional sources;
development tools (§12.2) are never user prerequisites. The MCP layer is the official Go SDK (§17, DR-21).
### 6.3 MCP and CLI
- The primary interface is an MCP server (`aiwe mcp`, stdio only) that the user's harness session starts; the session's lead agent organizes work through its tools: plan, work start, stop and status, models, sources, item (an idle agent asks for work with `aiwe item take`, K31), check, report (the generator of §8.5). One registry feeds MCP and CLI (DR-16). The skeleton is driven through the CLI (L3). No host harness is assumed (O13).
- MCP server start = session start = the model assignment refresh point (§8.1).
- Long work runs in a detached **work session**: an engine process that outlives the harness session. Starting it returns a work session id. MCP tools and `aiwe runs list` query it. `aiwe runs stop --run <id>` stops one run's tree, records `stopped_by_owner`, requeues the unit and charges nothing. `aiwe halt [--repo R]` (planned: stage work loop) stops every run tree and work session and writes a halt lease in the state root; every start, claim, loop iteration and stop-hook block refuses while it holds; `aiwe resume` is terminal-only (NIST SP 800-61 Rev. 3, containment).
- Self-update (L14), from `v0.1.0`, only for a binary installed from a GitHub Release. The binary decides its install source from its own path, matched against per-OS data rows of package-manager directories (Scoop, WinGet, Homebrew). A package-manager install prints the manager's update command instead. A Release install updates at MCP start, at most once a day, with one checker at a time (a lease, §6.6). The checker downloads the latest release and verifies the Ed25519 signature `checksums.txt.sig` of `checksums.txt` with the public key embedded in the binary (`crypto/ed25519`), checks the archive digest and switches on the next start. It refuses a version lower than or equal to the running one and stays within the running major (below 1.0.0, the running minor); crossing needs the terminal-only `aiwe update --major` (SemVer 2.0.0 items 4 and 8; the rollback attack of The Update Framework). Before `v0.1.0`: build from source.
- `aiwe version` prints the injected version without the `v` prefix (§17), else `unknown`. A command that targets a repository without a stored gate runs onboarding first (§7.1).
- **Close evidence** (the one place; §2, R5, §7.3, §8.4 and the bridge text cite it): a `done` unit has one of three evidences: a commit on the default branch whose `Closes` trailer names the item (§12.3), which the landing queue turns into the close when it lands (L60); a gate report path that the core records when a finding key turns green (§7.3); a bridge evidence file, until #269 removes the bridge. A manual close is only `cancel` with a reason, and `supersededBy` for a duplicate. A **parent closes by itself** (L22): a goal or epic becomes `done` when every child is `done` or `cancelled` and its own `done` checks pass; with no `done` entry of its own it closes on its children alone. It needs no trailer and no manual close. `aiwe status` accepts exactly these (planned #426).
- `aiwe status` is derived, never written (R8): it prints from the work store, the ledger and git — open goals with their child summary, running, ready, stale and blocked units, closing anomalies, the unshipped batch and open owner actions. It classifies every open item as `shipped-open` (a `Closes` commit on the default branch, still open), `batch-pending` or `no-work`, and every `done` item without a close evidence as `closed-no-evidence`; it runs after each ship and at session start, and `shipped-open` and `closed-no-evidence` are red (R5, R8). The only hand-kept status text of a project is its list "broken / live config" (K32); everything else in a status file is `aiwe status`. The handoff for another harness is `AGENTS.md` plus `aiwe status`.
- MCP surface: `aiwe mcp snippet` prints a config entry that calls the binary by name; `instructions` (≤ 40 lines, with the resolved roots), `prompts` (`plan-goal`, `open-unit`, `audit-unit`), `resources` (`item-template`, `roles/<id>`, `projects/<repo-id>/gate`), `tools` (every non-terminal command).
### 6.4 Disk layout
`core/platform.go` resolves three roots at run time; first hit wins (DR-3).

| Root | Holds | Windows | macOS | Linux and other POSIX | Override |
|---|---|---|---|---|---|
| state | `sources.json`, `sources.state.json`, `models.cache.json`, `assignments.json`, `ledger.jsonl` and rotations, `projects/<repo-id>/`, lease files (§6.6) | `%LOCALAPPDATA%\aiwe\state` | `~/Library/Application Support/aiwe` | `$XDG_STATE_HOME/aiwe`, else `~/.local/state/aiwe` | `AIWE_HOME` |
| cache | bare clones of repositories onboarded by URL and bare mirrors of onboarded local paths; leased slots (§6.5) | `%LOCALAPPDATA%\aiwe\cache` | `~/Library/Caches/aiwe` | `$XDG_CACHE_HOME/aiwe`, else `~/.cache/aiwe` | `AIWE_CACHE` |
| temp | run scratch and child result files, each in an owned directory (§5.15) under the operating system's temp directory | `%TEMP%` | `$TMPDIR` | `$TMPDIR`, else `/tmp` | the OS variable |

- Env names derive from the product constant. `repo-id` = normalised remote `host/owner/repo`, never a local path. Stored paths are relative and `/`-separated.
- Ceilings (default), enforced by the sweep: state ≤ 64 MB and ≤ 1 000 files; cache ≤ 2 GB and ≤ 2 000 files for bare clones; slots: N × (repository + dependencies), N from §6.6; temp: 0 directories without a live owner. Free disk before a slot is created ≥ 2 × the last measured slot size, else `no_disk`. Cleanup: ledger rotation, then idle slots, then bare clones least recently used first; still over → `footprint_exceeded`.
- OS rules: short temp names (`<temp>/aiwe-r/<pid>-<time>`) and git's long-path option on Windows; file sets compare exact case (paths differing only by case → `invalid`); clones set `core.autocrlf=false`; removal retries 5 times, 200 ms apart (default), then `residue_locked` for the next sweep.
### 6.5 Run isolation
Serves DR-10 and DR-11 (O33).
- **Canonical repository**: a bare clone in the cache root, of the remote or, for an onboarded local path, a bare mirror fetched from that path. A fetch writes only remote-tracking refs and objects, and landing (below) updates the mirror, never the user's checkout, branch or work tree (F11). The mirror's landed tip is offered to the user's repository as the ref `refs/aiwe/landed/<branch>`; the user's own branch moves only by the user (default).
- **Slot**: a persistent clone of the canonical repository, made once by `core.CreateOwned` with `core.autocrlf=false` as one directory directly in the cache root (`core.RemoveOwned` accepts no other place); its work tree sits inside that directory. `aiwe slot lease --repo R --sha S` takes a free slot; with none free and the pool below N it creates one; at N it waits and prints its queue position. N is the load-derived bound of `core/capacity.go` (DR-3). The lease file `<state>/projects/<repo-id>/slots/s<k>.lease` records the repository id, the slot number k, the path of the slot's owned directory (so k maps to that directory; the directory name is the owned random name) and the holder's pid, session and time. The lease file stays while the slot exists. A release clears only its holder fields. So the map from k to the directory is never lost. A run works only in its slot; `TEMP`, `TMP`, `TMPDIR` and `HOME` point into the run's scratch directory under the temp root; `AIWE_SLOT=k` goes to the child, and ports, test database names and build caches derive from k (port base + k, `test_k`).
- **Reset** at every lease: `git fetch` from the canonical repository · `git checkout --detach <base>` · `git reset --hard` · `git clean -ffdx` keeping only the stack profile's `KeepDirs` (§8.2) · `git worktree list --porcelain` showing the slot alone · the profile's restore command, only when the lock-file digest changed, and then a manifest of each `KeepDirs` directory (paths, sizes, modification times). **Verify**: `git status --porcelain --ignored` may show only `KeepDirs` lines, and `git worktree list` only the slot; any other line or entry marks the slot `dirty`, and it is removed and cloned again. A `KeepDirs` manifest that differs from the one recorded after the last restore marks the slot `dirty` too, so a run cannot leave content in a kept directory for a later run (F8; the cost of the manifest is `unknown` until measured). A lease never hands out a slot that is not clean.
- **Restore**: the restore command runs inside the slot with the package manager's own user-level cache; no junction, hardlink or dependency directory shared between slots. The lock file's integrity hashes (for example `go.sum`) are the check on the content of that cache; a stack without them reads `not_measured` for cache integrity (F8).
- **Environment**: the parent environment minus secret-shaped variables (every `credentialEnv`, tracker tokens, names containing `TOKEN`, `SECRET`, `KEY` or `PASSWORD`, names ending `_PAT`, `_PASS`, `_PASSWD` or `_DSN`, the last because a DSN always carries its key as the user part of its value, `NPM_CONFIG__AUTH`, the cloud credential-file variables named in `core/env.go`, and the value of a name ending `_URL`, `_URI` or `PROXY`: user info with a password, after a `://` scheme or at the front of any other value (so `svc:/pw@host` drops), a `:` with an `@` after it, or a user part without a password that starts with a known token prefix (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `glpat-`, `glft-`, `xoxb-`, `xoxp-`, `sk-`, `npm_`, `AKIA`). A user part without a password and without such a prefix is a name, not a credential, so `https://zeynep@host/x.git` and the scp-style `git@host:x.git` reach the child; case-blind) and minus the variables that reach a credential or a program outside the run (`reachNames` in `core/env.go`: git config parameters, askpass, SSH agent and exec path variables). **Value scan** (F4, #343): whatever the variable's name, a value is dropped when it begins with a known token prefix (the list above), when a `://` URL inside it carries one in its query string or fragment, or when a query parameter named `access_token`, `token`, `key`, `secret`, `password` or `sig` has a value; so a bare `FOO=ghp_…` and `SVC_URL=https://host/x?access_token=…` do not reach the child. The prefixes are data rows (DR-3). The adapter adds back only its own source's key. The harness starts with user-level rules, memory, hooks and plugins off through its documented flag or config-dir variable, which keeps its login. aiwe never copies or links a login file. `GIT_CONFIG_NOSYSTEM=1`, an empty env-set `credential.helper`, `GIT_TERMINAL_PROMPT=0` and `GIT_CONFIG_GLOBAL` at the null device cut git from user settings and helpers (§17). Every check process, the restore command included, gets the same environment. The environment, not the directory, carries this isolation, so a slot gets it unchanged.
- **Collect**: fetch the run branch into the canonical repository as `refs/aiwe/runs/<run-id>`, record residue (uncommitted paths, diff stat), release the lease (its holder fields only; the lease file stays with the slot); the slot stays and the next lease resets it. Path lists are read from git output, never passed as argv. A run ref holds unaudited code (F12): it lives only in the canonical repository, is never pushed on its own (the batch push of §7.3 step 11 carries audited tips), has that repository's access and no other, and is deleted when its item is `done` (§7.5).
- **Landing**: the canonical branch has one writer, the integration queue of §7.3 step 11, which takes audited run refs one at a time, rebases or cherry-picks each onto the batch tip and runs the fast gate. No agent and no interactive session writes the canonical working tree: a session leases a slot or only reads. Item writes (§8.4) are commits through the same queue. A commit that changes files under `work/` alone skips the code gate and never the trust checks (L20): it runs `aiwe item lint` with the ledger comparison of §8.4 (`reviews`, `status` and `close` must equal what the ledger's events say, so a hand-made, schema-valid item file cannot forge a verdict, F1), the secret scan and the bidirectional and HTML filter (F3, §7.10). A conflict at landing re-runs the item operation: an item commit that conflicts at rebase is rebuilt by re-running its recorded `aiwe item` operation, and a refused replay returns to its caller with the reason; no merge driver is installed (DR-4). This ends `index.lock` collisions and foreign files in a commit as a class.
- **Sweeper**: at start and after each run, reap the leases of dead holders (the slot is reset and freed), then remove temp directories whose owner process died (§5.15); a slot is removed only by the cleanup order of §6.4, and no idle-time rule shrinks the pool until a measurement shows what a fresh clone saves (the saving is `unknown`, last bullet). A slot goes nowhere else. A holder is dead when its process id is gone or now belongs to a process with another start time: every lease file and every temp directory's owner record names the pid and the process start time, and a pid alone never proves a holder alive (F8).
- **Temporary data** (O35, K36): create nothing where possible, in this order. (1) No file: data moves by pipe, stdin or memory. (2) Otherwise an owned directory under the operating system's temp directory (§6.4, §5.15), removed when the process exits; there is no `aiwe tmp` command and no temp root of aiwe's own. (3) The sweeper removes a dead owner's directory. (4) The ceiling of §6.4 turns an overrun red. (5) The repository gate, at pre-commit and session end, reports a new file that is neither tracked nor ignored; this one check covers repository residue, and no rule rejects a directory by its name.
- **Worktrees** (O34, K36): `git worktree` is not used. The core enforces it: the slot verify and the collect step read `git worktree list --porcelain`, a slot with a linked worktree is `dirty` (removed and cloned again), and landing refuses a run ref from it. A harness hook that rejects `git worktree add` and a subagent call with worktree isolation, and names `aiwe slot lease`, is an early warning only: one adapter row (§10.4). Reason: worktrees share refs, config and hooks and gave no speed gain (§17). Also rejected: `--shared` clones (they break when the source prunes) and file locks in place of a separate tree (§17).
- Measured: §17 (isolation, 2026-10-25). Unmeasured (`unknown`): the incremental restore after a lock-file change, a Python dependency repository, a content-addressed package store shared between slots, a cold cache; in the worst case a lease costs what a fresh clone costs.
### 6.6 Concurrent sessions (O11)
5 to 10 or more sessions work at once on the same or different projects without conflict, and with no daemon. A multi-agent team is assumed to work around the clock (O36): there is no day or night mode, and one method applies at all times.
- **Per project**: gate, stack, unit queue, the one work session, metrics and state under `<state>/projects/<repo-id>/`. `models.json` there holds optional pins and exclusions for this project, in the shape of `overrides` (§8.1). An MCP session binds to the project of its working directory and may target another by parameter.
- **Machine-wide**: sources and their quotas, the catalogue and the model assignment, CPU capacity.
- **Admission**: there is no fixed session run cap. Concurrent runs = Σ of the source ceilings, each ≤ its `maxConcurrent` (an owner value per source, default 10), over the ready units with disjoint file sets, each with a free slot (§6.5); a new run starts only on the load state `start` (`start`, `wait` or `stop`, from `core.LoadSample.Verdict` in `core/capacity.go`; test `core/capacity_load_test.go` TestLoadSampleVerdictThresholds). Each check, build and runtime process takes an admission ticket from the check executor's pool (#314 K18: pool = measured free cores, and the granted tickets set the worker count); an API loop run takes no ticket; a full gate takes the whole pool.
- **Coordination**: the project lock `work.lock` allows one work session per project; a second MCP session attaches to it. A project runs on one machine (K41), so a lease file is the whole mechanism: no remote ref, no push, no daemon. Four things are leased (L28), each by a lease file in the state root with a holder (session, pid and process start time), a time and an expiry that aiwe sets, released on exit and reclaimed from dead holders: a **slot** (a workspace clone, §6.5), a **ticket** (CPU admission), a **claim** (work ownership, below) and a **scope lease** (planned files, below). Only the engine appends to the ledger, under a lock (§8.5); `assignments.json` is written atomically; one refresher at a time reads catalogue and discovery.
- **Claim** (L19, K41, F2): the owner of an item holds the lease file `<state>/projects/<repo-id>/claims/<id>.lease`. It is created exclusively, so a second claimant is refused and the first wins. aiwe sets the expiry, never the holder: the time of the last renewal on aiwe's own clock plus one term, 5 min (default). The holder renews it at each heartbeat (§7.11), and a renewal that finds another holder's token fails and stops the run (`lost`, §7.4). A claim ends only by its holder (`aiwe item return`, or the unit's end, §7.3 step 13) or by its expiry; no other session deletes a live claim. An expired claim is reclaimed by one rename of the file to a tombstone, so two reclaimers cannot both win, and a crash frees the item with no human. The claim is the atomic part of ownership; the item file only shows it (L20).
- **Scope lease** (O33, K44): an item that becomes `active` leases its `scope.in` entries, the planned file paths and globs, as the lease file `<state>/projects/<repo-id>/scopes/<id>.lease`. A second item whose scope intersects a leased one does not start and joins the queue; the test is conservative: equal paths, one inside the other's directory, or a glob that matches the other's path. The gate runs in aiwe at item start, so it is the same on every OS and harness. Its purpose is to prevent merge conflicts, not to lock files: no OS-neutral file lock stops another process's write (§17).
- **Take and return** (K31): work is pulled. An idle agent asks, and aiwe knows which item is free. `aiwe item take --role R` (CLI and MCP) is one call and all-or-nothing, in this order: the load state is `start` (else the call holds nothing and returns the state); the first item of the role-filtered ready list (§8.4); its claim; `start` and its scope lease; a slot lease reset to the base commit (§6.5); its brief (`aiwe item brief`, §9.5). A step that fails releases the earlier ones in reverse order, and the call tries the next candidate; with none left it returns `none_ready` and holds nothing. *Ready for a writing role* is the `ready` list narrowed to the items whose resolved roles (§9.1) include R, and the session joins the item's `writers` (§8.4); *ready for a judging role* is an item with a collected run branch and no verdict of R yet, never one the session wrote to (DR-5). The reply holds the item id, the slot path and the brief. `aiwe item return ID` collects the run branch (§6.5), then releases whatever it still holds of the slot, the scope lease and the claim (the slot is already free after the pre-audit check in the lifecycle, §7.3 step 8); the status moves stay separate commands. Each is a `taken` or `returned` event of the ledger (§8.5). A ticket is not part of take: a check takes its own when it runs (§7.8).
### 6.7 Sandbox adapter
`Sandbox{Level(); Wrap(ctx, ChildSpec)}` with three levels (Q19): `env-scrub` (only §6.5; the agent runs with the
user's rights) · `harness-sandbox` (the harness's own documented sandbox, switched on by the adapter) · `os-sandbox`
(writes outside the clone, network beyond policy and reach into other processes blocked by the OS without elevated
rights). The skeleton ships `env-scrub`; every run record names its level; stronger levels: §15. An external tool may
implement the adapter if its level holds on three OS and the contract tests prove it. Open risk until then: an agent
can read and change what the user can, the ledger and `<state>/` included; the ledger is therefore tamper-evident and not tamper-proof (§8.5), and README and SECURITY say so (§12.1).
### 6.8 Machine tools
aiwe owns the tools that keep a machine usable while sessions work (L26), so no script outside the binary does their job (DR-3, DR-4): the check executor (`aiwe check <kind>`, §7.8), which runs every test, gate, build, survey and deploy through one heavy-job queue limited by tickets and prints the queue position; and `aiwe load show`, which prints the load sample and its state (`start`, `wait`, `stop`, §6.6). `aiwe check survey -- <command>` runs a heavy command (full test, mutation run, large fetch) and `aiwe check narrow` runs the profile's narrow test for the changed files (§8.2 `Narrow`, §7.10); `aiwe gates gate` and `aiwe verify` are the entry names of the kinds `gate` and `verify`. All read `core/capacity.go`.
## 7. Core flows
`[M]` mechanical · `[J]` agent judgement · `[O]` owner.
### 7.1 Onboarding — automatic, or `aiwe onboard --repo <path-or-url>`
1. `[M]` Resolve `repo-id`, canonical repository, working branch (remote default or `--branch`) and CI presence.
2. `[M]` A project `gate.json` → use it (DR-4) and go to step 5.
3. `[M]` Detect stacks (§8.2): `stack_detected`, `multi_stack` (§15), `unknown_stack` (§7.7) or `detect_error`.
4. `[M]` Derive gate steps whose tool exists and whose config is present.
5. `[M]` Prove the gate on the base commit in a leased slot reset to the base commit: each step `green`, `red_at_base` (stored `known_red`,
   reported, not blocking) or `not_measured`, with a measured duration.
6. `[M]` Store gate and proof under `projects/<repo-id>/` with the input hash; an unchanged rerun is `no_change`.

After onboarding, `aiwe init` (§11.3) writes the profile and opens items for the rows of the stage catalogue `catalog/stages.json` that bind and fail. The stage gate `aiwe stage next` prints the one binding, failing row that blocks the most others, and `aiwe sync` (§11.4) opens the work that closes any later difference.
### 7.2 Planning — `aiwe plan --repo R --goal <id>`, or the user's own session
Both paths use the `item-template` and the §8.4 record (R2). **Architect path**: `[J]` an architect run returns unit
records · `[M]` each record is validated; a failure returns once · `[J]` an auditor run (DR-5) audits the split
against the goal's `problem` and `done` entries and the file-set overlaps, and applies the necessity check (§4.1) when it triggers · `[M]` a second failure stops with
`plan_invalid` and an `owner-action` item · `[M]` valid records become child items with `blockedBy` links (L8);
an unchanged rerun is `no_change`. **Session path**: the user's session writes each unit as a record and runs
`aiwe unit check`; the store write waits for `aiwe item` (stage work store; the bridge `issue.py` until then, #314 K43). Intake reads the record again.
### 7.3 Unit lifecycle — `aiwe work --repo R [--unit ID | --goal ID]`, skeleton path (M-Skeleton)
| Step | Kind | What happens |
|---|---|---|
| 1 intake | M | Read the item through the tracker port (§10.1); read the record (§8.4) and run the intake gates (R3). Skip `owner-action` and blocked items. |
| 2 claim | M | One open run per unit: a claim, the lease file of §6.6, taken with the scope lease and the slot by one `aiwe item take` (steps 2 and 3 are that call). The base commit is the head of the remote working branch at claim. Units with intersecting file sets never run together (scope lease, §6.6). |
| 3 isolate | M | Lease and reset a slot (§6.5); failure → `isolation_failed`, and `aiwe item take` releases the claim and the scope lease it already holds. |
| 4 route | M | Resolve roles (§9.1); take each role's first available entry of the session assignment (§8.1). |
| 5 write | J | A behaviour unit's test is written at admission by the test-author (R6); the engine records the red proof on the test commit over the base. A base that moves before the run repeats the red proof and renews the tests when it fails to hold. Then the engineer or doc-writer writes the change on the run branch, with the role prompt (§9.2). |
| 6 verify | M | The engine runs the unit verify once per cache key when the agent asks through `aiwe verify` and returns red output to it. |
| 7 collect | M | Run branch to a run ref; residue recorded; lease released. |
| 8 scope check | M | Lease a slot at the run tip (step 7 released the run's lease). Apply the stack profile's `Fix` commands (§8.2; the Go row: `gofmt -w` on the changed files, `golangci-lint --fix` (only for linters that offer a fix), `go fix <changed packages>` and `go mod tidy`, which is module-wide by nature) as kind `fix` through the check executor under a ticket (§7.8) on the packages the run changed. The engine keeps only fix changes inside the declared file set. A fix change outside the set (`go.mod` or `go.sum` from `go mod tidy` included) is not kept. When the same `Fix` command makes that change on the base commit too, it is `pre_existing` (DR-9) and does not block. A change the run caused is a finding that names the file. A profile without `Fix` skips this. Commit the kept result on the run branch as the engine's own commit and collect it into the run ref, since work whose answer is fixed by its input is code, never a model call (DR-2). Then check `<base>...<tip>` against the file set (DR-9) and run the fast gate steps the diff touches (§7.10) at the tip as kind `gate` through the check executor under a ticket (§7.8), reusing recorded cache keys; then release the lease (DR-11). If a fix turns a test red, the engine reverts the fix commit, and the red record names the reverted tip. Dead code (deadcode, unused) and security findings (gosec, govulncheck) stay reports and are never removed or changed automatically. Only the findings that remain, red → the unit goes to the step 10 fix round with the red record, outcome `pre_audit_red`, and no auditor run is spent. The auditor (step 9) sees the engine's commit in the diff like any other and starts only on a green tip. |
| 9 audit | J | Every unit gets an auditor in a separate run with a clean context (DR-5); it compares the done criteria with the diff using engine evidence only. The #314 K2 residue (surviving mutants, D12/D13 flags, judgement done entries, any not_measured part of the set) widens that evidence and never decides whether the audit runs. The auditor's answer is a verdict record on the item (§9.5). Every `path:line` and identifier a RED verdict record cites must resolve on the tip, else `unverified_finding` and a new auditor run. |
| 10 fix loop | J | Returned or red → an engineer fix round, at most 2 (§7.4), then `quarantined`. **Fix delta**: the round resumes the run's recorded conversation while it is eligible (§10.3); else a fresh run whose task is the `FIX` section only: every failing item of the red record (#314 K13), the diff stat of `<base>...<tip>`, the RED findings with `path:line` and the previous return (≤ 12 lines); the card and the stable prompt prefix stay identical, so the prefix cache hits. A second red moves the next run up the assignment (§8.1 point 9). |
| 11 integrate | M | One batch in flight per project: a batch pull request starts when no batch is in flight and at least one audited commit is queued (bors-ng; DORA small batches). Push the run branch; queued unit commits ship as one batch pull request; wait for its CI (red → the batch is split in halves, a fix round, step 10); fast-forward `main` to the tested tip only while every unit commit still equals its own `AuditedTip` (DR-14), each unit commit keeping its own `Closes` trailer; a unit removed by the split stays open and returns as a fix round; a second refusal because `main` moved → `push_rejected`. Title: `<type>(<scope>): ` of the first non-test commit, then the item title with a lower-case first letter; the whole title is cut to 50 characters. Message per §12.3, written by the engine (L7, R5). A breaking marker waits for the owner (§12.3). |
| 12 main | M | No `main` push starts a run (§12.2); the green batch pull request is the merge evidence and `main` carries the tested tip. A red found on `main` after a batch merge → a revert pull request, merged once its CI is green; the unit item returns to `open` and requeues. Red revert CI → `revert_red`; no run in time → `ci_not_observed`. A goal or epic is finished by the engine after its last child finishes (§6.3). |
| 13 closeout | M | Append run and check records (§8.5); upsert units by finding key (R4); `aiwe item return` releases the scope lease and the claim (the slot went at step 8); delete the remote run branch. |

After each gate run the core upserts units by finding key (R4; there is no `aiwe item sync` command, L60): finding key red and no unit → create; red and a unit open → update its items; green → `done` with the report path (a close evidence, §6.3); a changed rule revision → the unit is `stale`, not dispatched, until the rule's check has run again. A conformance unit's parent is the milestone goal of its rule's registry row and its urgency comes from that milestone; a unit whose parent goal is finished is not dispatched; an item cites a rule and never copies its text (R10). Make one unit per finding-key cluster (rule × directory), placed in the area of that directory (§8.4). A new plan or an audit matches the open units of older goals by finding key mechanically: still wanted → move under the goal; green → `done` with evidence; no longer wanted → `cancel` with `supersededBy`; the unmatched rest goes to one bounded agent run (R4).

After the skeleton, these join (§13): an **already-done** check before step 3 (base verify; ambiguous → analyst); the gate steps that are not fast steps, in a leased slot at the tip after the pre-audit check of step 8, reusing recorded cache keys; **D-checks** and **mutation** before the audit (§11); **security-reviewer** and **ux-reviewer** beside the auditor (a `not_measured` UI review does not block, Q10); the **debugger** on a repeated red; the **ladder** (§7.7).
### 7.4 Failure paths
Red signature = step id + sorted failing test ids + exit code + first error line, with digits, hashes and temp paths normalised.

| Event | Outcome | Engine action |
|---|---|---|
| Two or more stacks; no known stack; detection fails | `multi_stack`, `unknown_stack`, `detect_error` | Stop (§15); ladder (§7.7); red. |
| No adapter can run ladder rung 2 | `artefact_requested` | The owner answers with `aiwe artefact submit`. |
| Unit text invalid; no role resolves; a tool result over its cap | `unit_invalid`, `role_unresolved`, `prompt_too_large` | Refused at write or intake, no item created; findings in the ledger and `aiwe unit check`. |
| Product decision; plan fails parse or audit twice; first 5 units of a goal (default) have M1 < 70 %; the change fail rate is over its target (M3); more than 5 tests of a repository are quarantined; revert pull request CI red | `owner_decision`, `plan_invalid`, `goal_paused`, `revert_red` | Stop the unit, goal or queue; an `owner-action` item that blocks it; ledger `owner_action`. |
| Gate or verify red, agent fault; zero tests collected; a fast gate step red at the tip before the audit; a `Fix` change outside the file set that the run caused; a fix reverted because a test turned red | `red`, `no_tests_collected`, `pre_audit_red` | Fix round; for `pre_audit_red` no auditor run is spent (§7.3 step 8). |
| Same red signature in two consecutive rounds | `repeated_red` | A debugger run; repeated again → stop, `owner-action` item. |
| Red from the environment (tool, network, timeout) | `environment` | Retry once in another leased slot with a `rerunReason`; still red → `not_measured`; not charged. |
| Isolation failed or disk short | `isolation_failed`, `no_disk` | Not started; queued; a second failure → `environment`. |
| Over the run limit, or silent past the silence limit | `timed_out`, `stalled` | Stop the tree; kill evidence (§7.8); an attempt. |
| Observed model differs; account restricted | `model_mismatch`, `account_restricted` | Not charged; next candidate (§8.1); a restricted source is set `restricted` (§7.6) with an `owner-action` item. |
| No candidate for a role | `no_capacity` | The unit waits; other roles continue. |
| `aiwe item take` finds no ready item for the role | `none_ready` | Nothing is held (§6.6); the reply names the first blocker per candidate, or the load state when it is not `start`. |
| A hook entry that `aiwe install` wrote is missing or changed when an item starts | `hook_drift` | The loop stops before the item; `aiwe install` repairs the entry (F5, §7.11). |
| No GitHub token (§10.1) | `tracker_unauthenticated` | No intake, CI read or pull request; exit 1 with the next action. |
| Conflict at integration | `conflict` | A resolution run on the rebased run branch; two failures → `skipped`, requeued (Q11). |
| Three failures on one unit; no CI run in the wait limit | `quarantined`, `ci_not_observed` | Not offered again; an `owner-action` item blocks it; never green. |
| Run process lost | `lost` | Requeued; the record closes with the time since `StartedAt` as an upper bound, never 0 ms. |
| Ledger not writable; ledger chain or landing anchor fails verification; footprint over after cleanup | `ledger_unavailable`, `ledger_tampered`, `footprint_exceeded` | No dispatch (`aiwe ledger verify`, §8.5). |
| Unanswered harness permission request; owner stops a run | `permission_blocked`, `stopped_by_owner` | Stopped, requeued, not charged; an `owner-action` item for the first. |
| API reply cut; the context estimate over its ceiling (E, below) | `answer_truncated`, `token_limit` | An attempt, never a finished run; the next run of a `token_limit` starts from the run ref with the previous return. |
| A unit commit differs from its `AuditedTip`; `VERDICT:` in a commit; RED cites what does not resolve | `unaudited_commits`, `verdict_in_branch`, `unverified_finding` | Refused; new auditor run for the last. |
| A red whose failing test ids are green at the base and lie in packages the diff does not touch | `suspect_flaky` | Rerun once for those ids (`rerunReason: suspect_flaky`). Red then green quarantines the test, not the unit (`test_quarantined`): it still runs and is recorded, does not gate for at most 7 days (default), and one fix item per test id opens. A quarantined test is not a skipped test (DR-12). |
| `vuln` red at the base for a module the diff does not change | `known_red` | One high-severity unit for that module; the unit under test goes on. A diff that adds or raises the vulnerable module stays red. |
| Red smoke check after a deploy | `rolled_back` | The engine dispatches the project's rollback job to the previous release without the owner and records it (§7.8). |
| Breaking commit | `breaking_change` | Not merged; `owner-action` item; `aiwe unit approve-breaking` (§12.3). |
| Unsafe root; failed removal check; locked file | `root_unsafe`, `not_owned`, `residue_locked` | Nothing removed (§5.15); next sweep retries a lock. |
| Invalid UTF-8; terminal-only command without a terminal; git missing or too old | `invalid_utf8`, `not_a_terminal`, `git_missing`, `git_too_old` | Refused or exit 1 with the next action; `invalid_utf8` names the first invalid byte. |

Outcomes named elsewhere that await an engine action here: `scope_mismatch`, `pre_existing`, `scope_outside_files`, `push_rejected`, `config_invalid`, `harness_missing`, `harness_incompatible`, `harness_unreadable`, `session_directory_mismatch`, `ceiling_unproven`, `capped` and `unknown_error` (planned #427).

**Context ceiling** (S5, §10.2): 200,000 tokens per API request, all-inclusive; a request is sent only while the
estimate E ≤ 184,000, else the run ends `token_limit` with its report and usage. E = the last reply's `prompt_tokens` +
the appended bytes ÷ b, where b is the run's lowest bytes per token (2.0 before the first reply); no tokenizer runs
(DR-21). At E ≥ 150,000 the oldest tool results become one-line stubs down to 100,000 in one batch; the system, task,
assistant and reasoning fields are never edited. Wind-down begins at 90 % of the run limit, or as soon as clearing
cannot get under 150,000. Read-only roles get only read tools.

**Limits from the ledger** (DR-1, L30), each printed with its basis. There is one limits derivation for every run limit, step limit and step budget. A limit is `max(floor, factor × percentile)` of the last 20 green samples of its kind; with fewer than 20, the default column holds.

| Limit | Sample | Floor | Factor | Percentile | Before 20 samples |
|---|---|---|---|---|---|
| Run, per role, source and model | green run durations | 30 min | 1.5 | p90 | the role's limit over all sources once that has 20 samples; else 60 min |
| Silence, per source | the longest output gap of each green run; time inside `aiwe verify` counts as output | 5 min | 2 | p99 | 10 min |
| CI wait for a batch | batch CI durations | 30 min | 3 | p90 | 30 min; the adapter polls every 30 s; expiry → `ci_not_observed` |
| Gate step, time limit (§7.8) | the step's green durations | 60 s | 3 | p90 | max(60 s, 3 × the base proof duration) |
| Gate step, budget (§7.10) | the step's green durations | none | 1 | p90 | the gate point's default budget |
| Turns, per role | turns of green runs | none | 1.5, rounded up | p95 | 100 |
| Output reserve `max_tokens` R, per role and model | per-turn completion tokens of green runs (the context ceiling above) | none | 2 | p99 | 16,000 |

- Fix rounds per role: 2 until 50 merged units; then the smallest r for which round r + 1 added under 10 % of the role's greens over its last 50 units, minimum 1.
### 7.5 Resume
State lives in refs, the tracker and the ledger. After a crash `work` marks open runs `lost`, reclaims claims past their expiry (§6.6) and releases scope leases and slot leases with no
live run, and collects then removes temp directories of dead owners. A run ref goes once its unit's item is `done`.
### 7.6 Quota exhaustion and account restriction
aiwe shows the state a provider reports and builds no forecast on it (K34). The adapter classifies an error from structured fields, never from message text alone (a text-only harness gets a per-adapter rule under its contract suite). A quota class sets the source `passive`, until the reset time the error states, else until the owner runs the terminal-only `aiwe sources enable <id>`; `account_restricted` sets it `restricted`, until the owner enables it. aiwe runs no probe, reads no balance endpoint and sets no reset time of its own. The run requeues without an attempt and takes the next candidate (§8.1), never a second account of the same provider (O7).

| Class | Detected by (§17) | Passive until |
|---|---|---|
| `rate_window` | HTTP 429 with `retry-after` or a reset header | the stated time |
| `provider_spend_limit` | a spend-limit error code | the stated reset, else the owner enables it |
| `balance` | HTTP 402 or a balance error with a limit source | the owner enables it |
| `subscription_window` | the harness's usage-limit result | the stated reset, else the owner enables it |
| `account_restricted` | HTTP 401 or 403, or a documented suspension code | the owner enables it; never probed, because a probe could deepen a ban (§17) |

A single text match never sets `restricted`. An unclassified error is `unknown_error`, an environment fault.
### 7.7 Adaptation ladder (DR-2, after the skeleton)
For gate steps, unknown-stack profiles, adapter config, the model-role mapping (§8.1) and unit decomposition: a stored artefact with the
same input hash is reused · rung 1: a mechanical derivation is proved and stored · rung 2: a synthesis run (architect
or engineer), verified by an auditor run and proved on the base commit or by an adapter dry run, stored as
`{artefact, inputHash, producerRunId, verifierRunId, evidence}`; no adapter → `artefact_requested` and the owner's
terminal-only `aiwe artefact submit`, then the same proof · rung 3: a product decision → an `owner-action` item.
### 7.8 Check execution (DR-8)
- **Central executor** (K30): an agent never runs a test, gate, build, survey or deploy itself; it calls `aiwe check <kind>` (CLI or MCP). The kinds are `verify` (a unit's verify; entry name `aiwe verify`), `narrow`, `gate` (entry name `aiwe gates gate`), `build`, `survey` (any other heavy command, given after `--`), `deploy` (`--env E`, which dispatches the project's own CI deploy job) and `fix` (changes the tree; never cached). Kind `fix` is not a check: it has no cache key, so DR-8 and the rerun rule do not apply to it. There is no daemon: the queue is a directory of ticket files in the state root (§6.6), and a waiting caller prints its position.
- **Queue**: one queue with four priority classes. 1: deploy. 2: the landing gate (§6.5). 3: narrow tests, unit verifies, the pre-audit fast gate and `fix` (§7.3 step 8). 4: surveys. When a ticket frees, the oldest request of the highest class starts; a running check is never preempted. Admission is by tickets from the measured pool (§6.6).
- **Deduplication**: requests with the same cache key that arrive together run once. The first holds an in-flight lease file named by the key, the others wait for it and read its stored result; a stored result under the key is served with no run (DR-8). Kind `fix` is not a check (above), so it always runs.
- **Result**: the caller gets the compact rendering of §7.9 and the path of the full log; the full output never enters the agent's context.
- **Deploy** (K43): a deploy is the project's own CI deploy job for one environment, dispatched by `aiwe check deploy --env E` on a green `main` tip. A credential stays in the CI environment and never reaches aiwe or a run (DR-19). On a project at stage `live` a deploy takes only a tip at which every goal with landed units is `done`; there is no feature-flag mechanism. The engine then runs the project's smoke check; red dispatches the project's rollback job to the previous release on its own and records `rolled_back`. A deploy that carries a commit of a risky unit with a `migrat` path (§9.1) is irreversible (DR-1) and waits for the owner. **Deploy lock**: one lock per environment, the lease file `<state>/projects/<repo-id>/deploy/<env>.lock`; a second deploy to that environment waits, a deploy to another environment runs in parallel. aiwe holds no deploy credential and reads none (§2).
- **Hook and enforcement** (K36, O34): a harness hook that sees a direct heavy command (a test runner, a linter, a build or a deploy tool) refuses it and names `aiwe check`. It is a thin adapter, one row per harness (§10.4), and an early warning only. The rule is enforced in the core: a result counts only when the executor recorded it, and the landing queue and `aiwe item close` read only executor records, so a direct run gains nothing. What the hook saves is the load of a direct run; below `os-sandbox` nothing stops a process the agent starts itself (§6.7).
- **Cache key** (`gates.CheckKey`, sha256), hermetic: the tree hash of the step's declared inputs (git objects; default the whole tracked tree) + the argv + the toolchain: OS, architecture, the output of the stack profile's toolchain probe (Go: `go env GOVERSION GOOS GOARCH CGO_ENABLED`), lock file digests and the values of the environment names the step declares (`env`, §8.3). A step that declares `network: true` (`vuln` included) adds the UTC date, so its result is not kept past a day (Bazel hermeticity; Nx and Turborepo environment inputs).
- **Rerun** of a cache key: only with a recorded `rerunReason`, once, after an environment-class failure or for a `suspect_flaky` red (§7.4).
- **Time limit** per step: the gate-step row of the limits table (§7.4).
- **Kill evidence**: the running step and, where reported, its test files or packages; machine load; the process table. Output streams to the evidence file during the run.
- **Partial run**: `gates gate --step a,b` prints "partial", never "gate green" (DR-6).
- **Zero tests**: a verify whose runner reports zero tests is `no_tests_collected` at any exit code; the profile names the signal (`NoTests`); Go prints `[no tests to run]` and exits 0 (§17).
- **Early diff checks** (after the skeleton): each `aiwe verify` also runs D1, D3, D4, D7, D10, D11 and D16.
- **Roots**: each check runs with all three roots in one fresh owned directory; an entry left there is red.
- When the last recorded verify's tree digest equals the final tree, it is the evidence. **Full gate only in CI** (L56): the full gate runs in CI, once per batch pull request, and CI runs every required step and takes no result from a local cache. Locally the landing queue runs the fast gate (§1.6, §7.10); a full gate runs locally only as a release rehearsal and when CI cannot be reached. The saving is `unknown` until the local full-gate runs and the CI minutes of the last 30 days are measured. Adapters add a harness command restriction where the harness supports one. Concurrent gates follow DR-3; slot waits are recorded apart.
### 7.9 One report format (R7)
Every result of a gate step, test, lint, D-check, mutation run and judging role becomes a `Finding`, stored as SARIF
2.1.0 (STD-6): `ruleId`, `level` (`error` = must, `warning` or `note` = nice), `message`, `locations` (path, line,
column), `partialFingerprints` (the finding key), `fixes` or `properties.fix` (one sentence; else the fix hint of the DR or STD rule's
registry row), `properties.evidence` (actual and expected). One file per check run; the ledger `check` record points
to it. The only text an agent sees is this deterministic rendering:

```
red: <step> (exit=N) — <n> findings in <m> files
<path>:<line>:<col>: <level>: <message> [<ruleId>]
  fix: <the change that clears it, one sentence>
+<k> more — <report path>
```

Sorted by path, then line; at most 20 findings by default; no colour (`NO_COLOR`); no stack trace unless it is the
only evidence (then at most 10 lines); identical input gives identical output. A failing test renders as its file and
line with `got … want …`. A tool with native SARIF output is used directly (`golangci-lint` v2
`--output.sarif.path`); other tools pass through an adapter (profile column `Failures`, §8.2). Every engine check
carries a one-line fix hint: in its registry row for a DR or STD rule, else in its own definition (§3, R9). The `finding:` grammar parses into the same record.
### 7.10 Gate points, budgets and the check register
A **gate point** is a moment at which checks run. One command serves them all, `aiwe gates gate --point commit|ci` (planned: stage gate timing); `gate.json` and the cache key (§7.8) stay as they are.

| Gate point | Runs | Default budget |
|---|---|---|
| edit | the editor's format and type check (not aiwe's) | none |
| commit | on changed files: format, lint, types; item lint (§8.4); secret scan and the bidirectional and HTML filter, on every commit and every landing, an item-only commit included (F3); item trailer (§12.3); diff budget (§4.1); test-integrity guard; doc-lint (§3.2) | 15 s |
| narrow test (optional, after commit) | `aiwe check narrow`: the tests that depend on the changed code (§8.2 `Narrow`) | 60 s |
| CI | the full test, build, security and dependency scan, migration lint, licence scan (§12.2) | the project's |
| merge | no merge unless CI is green (DR-14) | none |
| release | the deploy of §7.8: the project's CI deploy job, smoke test, automatic rollback; on a live project only a finished target | none |

- **Executor**: every row that runs a command runs it through the check executor (§7.8), so one queue, one cache and one pool of tickets serve all gate points.
- **Fast gate and enforcement** (K36): the landing queue runs the commit-point checks of the table on every landing, and the recorded unit verifies, so a commit made with no local hook is still checked; the local git hook is an early warning that runs the same checks. `aiwe install` or slot creation writes `core.hooksPath` in a slot, and the engine's own git calls use an empty one (§5.15).
- **Duration ledger**: every step writes its duration to the ledger `check` record (`durationMs`, §8.5). A step's budget is the derived p90 (§7.4) or a value its gate row sets by hand. A step over budget prints `slow: <step> 47 s (budget 15 s)` as a `warning` finding (R7); it does not fail the gate, the time limit (§7.8) does.
- **Check register**: the one list that says where each check runs. Each gate step names the error it `prevents`, its `point`, its `rule` (a registry id) and its `budgetSeconds` (§8.3). Two-point lint: the same check (equal argv) at two gate points is yellow. Exception, written in the row with its reason: a commit-point check runs once more in CI, because a local hook can be skipped in another harness and the repeat costs seconds; the `static` job of §12.2 is that exception.
- **Test integrity** (D2, D9): a commit that changes a test file, a CI workflow or a gate script together with product code is refused at the commit point unless the item's `scope.in` names those files; a drop in the assertion count (D9) turns CI red. Reason: DR-12.
- **Agent experience (AX)**: can an agent run the right test within seconds? The measure is the duration of the narrow test for the changed files, kept in the gate report; its target is `unknown` until the first measurement.

### 7.11 Unattended work
Unattended means no human waits and every gate still runs (§1.6). The owner's presence is the one switch (O26). Two mechanisms share one rule set.

**Stop hook** (`aiwe hook stop`; planned: stage stop hook). `aiwe install` (§10.4) installs it; it is the one hook a lead session cannot do without, because only the harness can refuse a stop (O26). In this order:
1. The owner is present (attended) → allow the stop.
2. The `--until` time is reached → allow; reason `until`.
3. The ready list (`aiwe item ready`, which leaves out `waiting` and `deferred`) is empty → allow; reason `queue-empty`, or `all-waiting` when open items only wait.
4. The same item has failed 3 times → mark it `quarantined` (§7.4) and take the next.
5. The harness reports that this hook already blocked the stop (the adapter row names the field) and 3 or more consecutive blocks passed with no tool call → allow; the work loop takes over (loop guard).
6. Otherwise block, with the reason: "Do not ask. Decide and record it in the item, or park the item with `aiwe item wait`. Next item: <id> <title>."

The ready list decides, not the model. The decision is one function of the core that the stop hook, the work loop and the MCP tools call; the hook only passes it on (K36). A question to the owner becomes a `waiting` item and the agent moves on. The harness's own block cap is left alone (§17): a running agent resets its counter at every tool call, and an agent that reaches the cap is not progressing, so the work loop is the right owner. A session-start hook injects the `active` and `waiting` items with their `handoff` into a new session. A harness without a stop hook relies on the work loop; each harness adapter writes its own hook entry from this logic.

**Work loop** (`aiwe work`; there is no separate `aiwe loop`, L21; planned: stage work loop). `aiwe work --until TIME --max-turns N` takes a sleep inhibitor (Windows `SetThreadExecutionState`, macOS `caffeinate`, Linux `systemd-inhibit`; one data row per OS, DR-3) and repeats: call `aiwe item take` for the session's role (§6.6), which returns the first ready item whose claim, scope lease and slot all succeed; run a session on it through the provider port (§10.2) under the limits of §7.4; record start, end, exit code, session id, cost and item; let the engine run the verify. Green → the lifecycle of §7.3 goes on. Red → the attempt count rises, and 3 reds quarantine the item. Time or turns spent → exit with the reason (`until`, `max-turns`, `queue-empty`, `all-waiting`). Cost is shown when the provider reports it and stops nothing (K34). Each item starts in a clean context, so context compaction is not a factor. The adapter passes the turn cap as the harness's own flag where it has them and reads the stop reason from its structured output; where the harness reports none, the reason is `unknown` (§17). A headless session has no permission prompt: its rights are limited by the harness settings and its pre-tool hooks. The destructive-command guard of `aiwe install` is in place before the first loop, but it is an early warning against accidents and not a barrier: an agent at `env-scrub` can edit its own harness configuration (§6.7). So the loop compares every hook entry `aiwe install` wrote with its adapter row before each item and stops with `hook_drift` when one is missing or changed (F5, fail closed), and the rules are enforced in the core, at the harness-neutral points: the git hooks, the landing queue and the CLI and MCP calls (K36). Once a week the loop runs an incremental `aiwe sync` (§11.4).

**Session end record** (planned: stage stop hook). The core writes a heartbeat, a time stamp in `<state>/sessions/<session>.beat` (overwritten), on every aiwe MCP or CLI call and at every loop turn, at most once per 60 s; a harness post-tool hook is an optional early signal. Each session ends with one ledger record of kind `session` (§8.5): reason, exit code, last heartbeat and the count of open items. A start that finds a heartbeat file with no end record writes that record with reason `lost` and the last heartbeat as its time. So a night that ended for an unknown reason can be explained from aiwe's own record.

**Hardware**: the sleep inhibitor needs no manual setting. The power plan and the Windows Update active hours are the owner's one-time `owner-action`; `aiwe doctor` reads them and warns, and never changes them.

### 12.3 Release
**svu + GoReleaser OSS** (§17): the next version comes from Conventional Commits with no release pull request, version
file or human choice; GoReleaser alone creates no tags, and release-please needs a release pull request and a personal token.

Release job: (1) checkout with tags; (2) `svu next`; equal to the current tag → `no_change`; (3) dry mode until
M-Release closes (L9): print the version and stop; (4) live: `git tag`, `goreleaser release --clean` (six targets,
archives, `checksums.txt`, the GitHub Release with notes, Scoop, winget and Homebrew manifests); (5) `actions/attest` on
`checksums.txt` (`contents: write`, `id-token: write`, `attestations: write`), then
`gh attestation verify dist/checksums.txt --repo "$GITHUB_REPOSITORY"`; (6) sign `checksums.txt` with the Ed25519
private key held as a CI secret and publish the signature as the asset `checksums.txt.sig`, for self-update (L14); (7) publish the `mcpb` registry entry.

**Commit messages** (here and in managed projects): the Conventional Commits header is ≤ 50 characters, `type(scope): `
included. Body lines are ≤ 72 characters; URLs, trailers and quoted command or output lines are exempt. A unit commit
carries exactly one `Closes: <item-id>` trailer and no `Refs:`; a commit that belongs to an item without closing it carries `Refs: <item-id>`; a commit with no item carries neither (R5, L33). The landing queue closes an item when a commit with its `Closes:` trailer lands on the default branch (§6.3, L60). An item-only commit (it changes files under `work/` alone) carries no `Closes:`. **Cutover** (L61): until stage G1 lands, the rule stays the current one, `Closes <owner>/<repo>#N` in a unit commit and no issue trailer in any other commit, and `repocheck commit-msg` enforces it; when G1 lands, `aiwe item migrate --from github` runs, `work/` becomes the one source, the GitHub issues close with a pointer to their item, and the item-trailer rule above switches on for this repository.
The closing commit carries `Effect: <before> → <after>` with measured values. Engine commits carry `Run-Id: <ULID>`; a landing commit also carries `Ledger-Head: <sha256>`, the hash of the newest ledger record at the landing (§8.5).
`external` commits (outside contributors) are exempt from the trailer and `Run-Id` rules; `owner` commits (for an `owner-action` item) are exempt from the `Run-Id` rule (Q17).
`repocheck commit-msg` checks this repository's commits; the engine composes its own messages to the same rules.

Rules: versions follow L9 (`v0.1.0` at M-Release, `1.0.0` at M-Trust); bumps (§17): breaking → major, `feat` → minor,
`fix` → patch, others → none. A breaking marker is a red line (DR-1): `breaking_change` until the owner runs
`aiwe unit approve-breaking`. No version in any file; GoReleaser injects the tag; `repo/source-rules` rejects version
literals. Release notes (Q15): Keep a Changelog layout via `changelog.groups` (`feat` → Added, `fix` → Fixed, others →
Changed); CI never commits to `main`. Provenance: one attestation, verified with `gh attestation verify` or
`checksums.txt`; cosign rejected. Code signing: Q7. The job runs only on a `main` dispatch, after `required` is green.
